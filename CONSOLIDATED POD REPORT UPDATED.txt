Project SENTINEL - Consolidated POD Report 

Project SENTINEL aims to develop a domain-specific fraud intelligence system for 
PayVista Payments Pvt. Ltd. The proposed system, SENTINEL-LM, must analyse 
transactions, estimate fraud probability, return an ALLOW, REVIEW or BLOCK decision, 
and provide a plain-language explanation.  

The supplied Supabase database kit contains synthetic development data organised into 
14 relational tables, one model_features view and 43 training-related files in the 
sentinel-data Storage bucket. It supports data exploration, feature validation, model 
development and testing.  

1.​ Dataset Overview 
1.1.​ Purpose and structure 

The dataset supports the development and evaluation of fraud detection, risk scoring, 
decision-making and explanation generation. Its relational structure separates raw 
transactions, fraud labels, engineered features, payment outcomes and supporting 
documents.

The model_features view combines transaction information, engineered features, 
customer attributes and labels. The exact number of columns in this view and the 
individual tables should be verified against the live schema or data dictionary. 

1.2.​ Production versus development data 

The client requirements describe a separate production dataset of approximately 12 
million transactions across 14 months, January 2025 to February 2026, with a fraud rate 
of approximately 0.6%. The Supabase kit contains 110,000 synthetic transactions and is 
intended for classroom development and testing.

4.​ Data Quality Observations 

The client’s production specification identifies approximately 3% missing 
customer-location values and some older UPI transactions with missing device IDs. Rare 
transactions exceed ₹10 lakh, and fraud represents approximately 0.6% of the 
production dataset—roughly one fraud case per 167 transactions. These are expected 
production characteristics, not verified findings about the synthetic Supabase data. 

Required checks include: 

●​ Missing values: quantify nulls in locations, device IDs and average transaction 
values; verify missingness flags. 

●​ Duplicates: check uniqueness of primary keys and duplicate document content.

4. Data Quality, Leakage and Privacy
These checks were run against the Supabase development dataset. The results describe the supplied synthetic data and should not be treated as evidence about PayVista’s production data. model_features is a view of model-ready data, so its results overlap with the underlying tables and are not additional records.

4.1 Duplicate and relationship checks
The primary-key and declared unique-key checks returned no rows: no duplicate key values were detected in the checked keys. The orphan-row checks for declared foreign keys also returned no rows: no orphan references were detected.

The database declares relationships from transactions to customers, devices and merchants; from features, labels, payment outcomes, gold explanations and preference pairs to transactions; from documents to transactions and legacy cases; and from legacy cases to customers. The corresponding checks found no non-null foreign-key values without a matching parent record. Nullable references in documents are not orphans, but their intended meaning should be confirmed separately.

4.4 Leakage controls
Several fields require explicit controls before model training:

model_features.fraud_label is the target and must not be used as a predictor.
mcc_target_encoded_rate is derived from fraud labels. Generate it using training-only, out-of-fold or time-aware encoding. Do not calculate it using validation, test or future labels.
Transaction history features such as previous_transactions, failed_transactions, txn_count_last_1h and txn_amount_last_24h_paise must use only events available before the transaction being scored.
payment_outcomes fields and investigation or explanation data may be recorded after a transaction decision. Exclude them from a real-time prediction unless their availability at scoring time is established.
Split training and evaluation data by time, and where appropriate by customer, to reduce leakage from related transactions appearing in both sets.
These are modeling safeguards to verify; the query results alone do not prove that leakage occurred.

4.5 Privacy considerations
The kit is described as synthetic, so these results do not establish that it contains real customer information. However, fields such as customer identifiers, age, location, device identifiers, transaction histories and investigation documents are sensitive in a production setting. Use least-privilege access, restrict access to raw identifiers and documents, apply retention limits, and use de-identified or aggregated data for analysis where possible. Avoid including customer-level records or document contents in the report. Reassess privacy and access controls before using any real PayVista data.



5.​ AI/ML Opportunities

First of all, preprocessing will include removing duplicate records, handling missing values, validating transaction amounts and timestamps, redacting PII from text, and encoding categorical variables. The target variable is fraud_label (0 = genuine, 1 = fraud). Engineered features include amount-to-average ratio, new-device indicators, customer–merchant distance, transaction velocity, and recent failures. ML models can be used with structured transaction data, while LLM can learn from approved text corpora and reviewed explanations. Batch processing can support historical training and periodic updates; real-time processing can calculate transaction features and return fraud scores and decisions. 

1.​ Supervised fraud classification: Train ML model using transaction and 
engineered features. Handle class imbalance with suitable class weighting or 
sampling applied only to training data. 

2.​ Risk scoring and decisioning: Calibrate probabilities and evaluate precision, 
recall, PR-AUC, false declines and fraud loss. Choose ALLOW/REVIEW/BLOCK 
thresholds using business costs and review capacity. 

3.​ Domain-adapted language model: Use approved investigator notes, dispute 
narratives, playbooks and reference documents for continued pretraining where 
appropriate. Use reviewed prompts and gold explanations for supervised 
fine-tuning. 

4.​ Grounded explanations: Generate concise reasons based on actual features and 
approved evidence; prohibit invented evidence and sensitive-data reproduction. 

6.​ Discussion Notes: Observations, Questions and Decisions 

Key observations 

●​ The dataset separates transactions, labels and features, supporting safer model 
development. 

●​ Transaction context is important: amount anomalies, new devices, new locations, 
recent failures and transaction velocity may jointly indicate risk. 

●​ Fraud labels may become available well after authorisation; label timing must be 
respected. 

Questions to resolve 

●​ Which document types are eligible for continued pretraining and which are 
approved explanation targets? 

●​ How will model drift, threshold changes and human overrides be monitored? 

Proposed decisions and learnings 

●​ Treat the supplied Supabase kit as synthetic development data. 



●​ Preserve train, validation and holdout boundaries. 
●​ Validate data quality, explanation faithfulness, calibration, privacy and 

end-to-end latency before deployment.
