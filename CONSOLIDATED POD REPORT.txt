Project SENTINEL - Consolidated POD Report
Project SENTINEL aims to develop a domain-specific fraud intelligence system for PayVista Payments Pvt. Ltd. The proposed system, SENTINEL-LM, must analyse transactions, estimate fraud probability, return an ALLOW, REVIEW or BLOCK decision, and provide a plain-language explanation. 
The supplied Supabase database kit contains synthetic development data organised into 14 relational tables, one model_features view and 43 training-related files in the sentinel-data Storage bucket. It supports data exploration, feature validation, model development and testing. 
1. Dataset Overview
   1. Purpose and structure
The dataset supports the development and evaluation of fraud detection, risk scoring, decision-making and explanation generation. Its relational structure separates raw transactions, fraud labels, engineered features, payment outcomes and supporting documents.

	The 14 tables contain 359,208 table rows in total, counting each table separately. This is not the number of unique transactions because several tables refer to the same transaction. There are 110,000 transaction records, with corresponding payment outcomes, labels and feature records.
The model_features view combines transaction information, engineered features, customer attributes and labels. The exact number of columns in this view and the individual tables should be verified against the live schema or data dictionary.
   2. Production versus development data
The client requirements describe a separate production dataset of approximately 12 million transactions across 14 months, January 2025 to February 2026, with a fraud rate of approximately 0.6%. The Supabase kit contains 110,000 synthetic transactions and is intended for classroom development and testing.

	4. Data Quality Observations
The client’s production specification identifies approximately 3% missing customer-location values and some older UPI transactions with missing device IDs. Rare transactions exceed ₹10 lakh, and fraud represents approximately 0.6% of the production dataset—roughly one fraud case per 167 transactions. These are expected production characteristics, not verified findings about the synthetic Supabase data.
Required checks include:
* Missing values: quantify nulls in locations, device IDs and average transaction values; verify missingness flags.
* Duplicates: check uniqueness of primary keys and duplicate document content.
5. AI/ML Opportunities
1. Supervised fraud classification: Train ML model using transaction and engineered features. Handle class imbalance with suitable class weighting or sampling applied only to training data.
2. Risk scoring and decisioning: Calibrate probabilities and evaluate precision, recall, PR-AUC, false declines and fraud loss. Choose ALLOW/REVIEW/BLOCK thresholds using business costs and review capacity.
3. Domain-adapted language model: Use approved investigator notes, dispute narratives, playbooks and reference documents for continued pretraining where appropriate. Use reviewed prompts and gold explanations for supervised fine-tuning.
4. Grounded explanations: Generate concise reasons based on actual features and approved evidence; prohibit invented evidence and sensitive-data reproduction.
6. Discussion Notes: Observations, Questions and Decisions
Key observations
* The dataset separates transactions, labels and features, supporting safer model development.
* Transaction context is important: amount anomalies, new devices, new locations, recent failures and transaction velocity may jointly indicate risk.
* Fraud labels may become available well after authorisation; label timing must be respected.
Questions to resolve
* Which document types are eligible for continued pretraining and which are approved explanation targets?
* How will model drift, threshold changes and human overrides be monitored?
Proposed decisions and learnings
* Treat the supplied Supabase kit as synthetic development data.
* Preserve train, validation and holdout boundaries.
* Validate data quality, explanation faithfulness, calibration, privacy and end-to-end latency before deployment.
